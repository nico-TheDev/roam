# Roam

Expo React Native rental app. Guests describe a stay in one sentence ("quiet pet friendly cabin with a hot tub under $300 a night") and get ranked stays back. They can also ask booking and policy questions about a stay, answered with exact text from Roam's own content.

This file is the project's memory: it holds every decision that is still true. Plans in `prompts/` are history.

## Commands

~~~bash
npx expo install <package>  # ALWAYS use instead of npm install: resolves SDK-compatible versions
npx expo start              # dev server (press i for the iOS simulator)
npx expo lint               # lint
npx tsc --noEmit            # type check
npx expo-doctor             # diagnose dependency and config issues
npx expo install --fix      # fix incompatible package versions
cd landing && npm run dev|build  # marketing site (Astro), own dependencies
npx eas-cli@latest <cmd>    # EAS builds, submits, and updates (use instead of bare `eas`)
~~~

## Expo

- Expo ships breaking changes every SDK release, so don't trust memory. Before touching an Expo, EAS, or React Native API, check the `expo` major version in `package.json` and read `https://docs.expo.dev/versions/v<major>.0.0/`. For anything else, start from https://docs.expo.dev/llms.txt and follow its links.
- Routes live in `src/app/`: every file is a screen and `_layout.tsx` files define navigators. API routes are `src/app/api/*+api.ts`. Keep components, hooks, and utils outside `src/app/`.
- `ios/` and `android/` are generated. Never create or edit them by hand; configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, switch to a development build (`npx expo run:ios`).

## Who owns what

Each tool has one job. Ask before moving a responsibility to a different tool.

- **Auth:** Clerk is the source of truth. The app keeps its own custom auth screens, built on `useSignUp` / `useSignIn` / `useSSO` from `@clerk/expo` (method-based API, never the legacy `setActive` flow except for SSO). Instance settings change through the Clerk MCP (`patch_instance_config`, dry run first). Profile edits, sessions and deletion go through `src/lib/account.ts` (`user.update`, `user.setProfileImage` with a base64 data URI from `expo-image-picker`, `user.getSessions` / `session.revoke`, `user.delete`). Delete is client side, shown only when `user.deleteSelfEnabled` (Clerk Dashboard setting), and reverified with `useReverification` + a password field (`session.startVerification` / `attemptFirstFactorVerification`); Google-only accounts must sign in again first. Dev instance: email + password, email-code verification, device trust on (new devices get a code on sign in), first/last name on, password min 8, Google on, Apple off.
- **Saved stays:** private per-user stay IDs live in Clerk `unsafeMetadata.savedStayIds`, never in the public Sanity dataset. Access only through `useSavedStays` in `src/lib/saved.ts` (shared optimistic copy, 400 ms debounced write, rollback with an error on failure, capped at 100 because Clerk metadata is 8 KB). Write with `user.updateMetadata` (deep merge); `user.update` replaces the whole object. Move to a database only when trips and bookings need one; only this hook changes.
- **Content:** Sanity project `a4so5rrr`, dataset `production`. Three document types: `property`, `host`, `policy`. Hosts and policies are shared documents that stays reference (one host, one cancellation policy, a list of other policies). Everything guests filter on is a typed field on `property` (`category`, `nightlyPrice`, `maxGuests`, `petsAllowed`, `amenities` from a fixed list, `location.city|state`). Soft intent lives only in prose on the property (`summary`, `description`, `neighborhood`), never in a `tags` field. Policy `body` is plain text, quoted word for word. Studio is a standalone app in `studio/` (hosted at `roam-rentals-a4so5rrr.sanity.studio`), and its source is the only schema: deploy it with `cd studio && npx sanity schema deploy` and `npx sanity deploy`, never the MCP `deploy_schema` (that creates a competing MCP-managed schema). Content changes and checks go through the Sanity MCP, and generated property copy uses Agent Actions.
- **Landing page:** Astro static site in `landing/` (Tailwind v4, tokens copied from `src/global.css`, own `package.json`, installed with plain `npm install` there). Not part of the Expo app; `tsconfig.json` and ESLint ignore it. v1 is one page: full-bleed dusk hero photo with a live typing search demo, a seeded-stay photo gallery, filters-vs-ranking explainer, policy answer sample, hosting, and a sunset close. Photos are Unsplash placeholders and the stays in `landing/src/data/demo.ts` come from the seed (labelled sample). The hero phone is a CSS iPhone (titanium frame, Dynamic Island, status bar, app tab bar) that tilts toward the pointer. Motion: one hero entrance on load, then scroll reveals via `data-reveal` + an IntersectionObserver in `Base.astro` (content shows by default; the `js` class that hides it is removed if the script never starts), all gated by `prefers-reduced-motion`. No store badges or CTA buttons until real store links exist. Theme follows the OS and a header toggle sets `data-theme` (stored in `localStorage`, applied by an inline script in `Base.astro`); dark token values live under both the media query and `:root[data-theme="dark"]`. Hosting not chosen yet.
- **Seed data:** `cd studio && npx sanity exec scripts/seed.ts --with-user-token` (data in `studio/seed/`). Idempotent by `slug.current` with Sanity-generated IDs: it creates what is missing and skips what exists; add `-- --update` to overwrite seeded fields. It uses the CLI login, so it needs no token. The seed fills `vibeNotes` on existing stays when missing.
- **Generated copy:** `summary`, `description` and `neighborhood` are written by Agent Actions (Generate, `noWrite`) from a stay's typed fields plus `vibeNotes` only (`copyFactsHash` records the facts used), and written to Sanity only when `studio/seed/check-copy.ts` finds no invented number, place, amenity, feature, pet claim, unsupported soft word or sales language. Run `cd studio && npx sanity exec scripts/generate-copy.ts --with-user-token -- [--baseline|--dry|--force|--only <slug>]`; unchanged facts are skipped. To change what copy may say, edit `vibeNotes` in Studio, then rerun. Self-test: `npx sanity exec scripts/check-copy-selftest.ts`.
- **Exact constraints** (price, guests, type, amenities, pets, place): GROQ filters. Search runs through the `roam-search` GROQ-mode Context endpoint (`SANITY_CONTEXT_MCP_URL`, organization token `SANITY_API_CONTEXT_TOKEN`, tool `groq_query`), which takes no params, so `src/lib/search-query.ts` writes allowlisted literals only (strings must be on a fixed list, numbers bounded integers; guest and model text never enter the query).
- **Soft intent** (quiet, cozy, secluded): Dataset Embeddings, enabled on `production` with a property-only projection (`title`, place, `category`, `summary`, `description`, `neighborhood`, `vibeNotes`; no references), used as `score(text::semanticSimilarity("…"))` after the hard filters, from `src/app/api/search+api.ts` with only the wanted vibe words (quiet, cozy, …) as the text; leftover keywords are no longer used, and an avoided vibe can't be excluded, so it only shows as a chip. Status: `cd studio && npx sanity datasets embeddings status production`. Queries count against the monthly semantic quota.
- **Policy knowledge:** the `roam-policies` Sanity Context endpoint in Knowledge Base mode (`SANITY_CONTEXT_KB_URL`), read by `src/lib/ask-server.ts` through `src/app/api/ask+api.ts` (entries loaded with `initial_context` + `knowledge_base_read`, cached 10 min). Context endpoints are created in the Dashboard's Context app and read with an organization token (Context Viewer), per https://www.sanity.io/docs/ai/context-migration-guide. One endpoint serves one mode. The Context skill still describes `sanity.agentContext` Studio documents with a project token; that route is deprecated, so don't use it.
- **Search reading:** DeepSeek (`deepseek-v4-flash`, thinking off, 5 s timeout) through `@ai-sdk/deepseek` and `ai` (pinned exact), `DEEPSEEK_API_KEY`, called from `src/lib/search-server.ts` with `generateText` + `Output.object` and a `jsonSchema` built per request. Code finds every option (`findCandidates` in `src/lib/search-intent.ts`: facets for pets, amenities, categories, vibes, plus number candidates); the model only labels each facet wanted / avoided / not_mentioned and each number max_price_per_night / min_price_per_night / guests / ignore. Anything off the sheet fails validation and falls back to the regex reading (`interpreter: fallback`); a sentence with nothing to read skips the model (`code`). No AI Gateway.
- **Bookings:** private records live in Neon Postgres (`DATABASE_URL_POOLED`, Drizzle, `src/lib/db/`, migrations in `drizzle/`, applied with `npx drizzle-kit migrate`). `booking_holds` are pending reservations (15 min, `BOOKING_HOLD_MINUTES`), `bookings` exist only after Stripe confirmed payment, `stripe_events` dedupes webhooks, `customers` links a Clerk user to a Stripe customer. Exclusion constraints on date ranges (migration `0001`) make double-booking impossible; checkout also takes a per-stay advisory lock. The server prices every quote and checkout from the live Sanity API (`src/lib/booking-server.ts`, rules in `src/lib/booking-rules.ts`: nights x nightly price + cleaning fee in cents, no taxes yet, max 30 nights, 365 days ahead); the app never sends or decides an amount. Only `finalizePayment` (`src/lib/booking-finalize.ts`) creates a booking: it asks Stripe, checks amount and currency, books in one transaction, and refunds when an expired hold's dates were taken. The webhook and `GET /api/bookings/status` both call it, so a late webhook can't strand a paid guest. The client never creates a booking.
- **Payments:** Stripe test mode only (`STRIPE_SECRET_KEY` must start `sk_test_` unless `BOOKINGS_LIVE=1`), PaymentIntent + PaymentSheet through `src/lib/stripe-native.tsx` (the only import of `@stripe/stripe-react-native`; its `.web.tsx` stub keeps `expo export --platform web` working), `EXPO_PUBLIC_STRIPE_PUBLISHABLE_KEY` in the app, `stripe` server side with `createFetchHttpClient` and `constructEventAsync`. Webhook `/api/stripe/webhook` handles `payment_intent.succeeded|canceled|payment_failed`. Local: `stripe listen --api-key $STRIPE_SECRET_KEY --events payment_intent.succeeded,payment_intent.payment_failed,payment_intent.canceled --forward-to localhost:<port>/api/stripe/webhook`. `stripe trigger payment_intent.succeeded` is broken for this API version; confirm a real PaymentIntent with `pm_card_visa` instead.
- **Hosting:** any signed-in guest can become a host (Profile > Hosting, `/api/host/join`); Clerk Organizations stays off. Ownership is `host.ownerKey`, an HMAC of the verified Clerk user ID with `HOST_OWNER_SECRET` (never the raw ID, the dataset is public); a stay belongs to the host its `host` reference points to. Every host read and write goes through `/api/host/*` (`src/lib/host-server.ts`, plain `fetch` to the live Sanity API with `SANITY_API_WRITE_TOKEN`); not-yours and not-found are both 404. Hosts manage stays from the Hosting screen: `GET /api/host/bookings` lists current and upcoming confirmed bookings on their stays (checkout today or later; dates, guests, amount paid; never guest data; `bookingPhase` in `booking-rules.ts` marks "Staying now" / "Checks out today"), `PATCH /api/host/stays/[id]` takes any add-stay field plus `listed` (validated by `stayErrors`; a change to a fact behind the copy regenerates it with `writeCopy`, 422 and nothing written on failure; older stays are only held to the fields being changed unless the copy is rewritten), `property.listed` (missing = listed) pauses a stay (filtered with `listed != false` from Home, Search, Saved and the host sheet; still opens by link with a banner; quote and checkout return 409 `paused`), and they add stays (`host/add`, `POST /api/host/stays`): photos 5-30 uploaded one by one to `POST /api/host/photos` (jpeg/png/webp, 10 MB), the core facts, check-in (12:00-20:00, default 15:00) and check-out (08:00-13:00, default 11:00) times and 3-6 `vibeNotes`, limits shared by app and server in `src/lib/host-stay-rules.ts`, max 10 stays per host. The server sets `host`, `slug`, `rating`/`reviewCount` 0, the shared policies and `copyFactsHash`, and writes the copy with the same Agent Action prompt (`studio/seed/copy-prompt.ts`, shared with `generate-copy.ts`) and `check-copy`; failing copy returns 422 and creates nothing. States are limited to those in `check-copy.ts`.
- **Typed decisions** (Jev, `experimental_evaluate`, `@ai-sdk/typesafe-ai`, `TYPESAFE_AI_API_KEY`): no feature uses it today. Policy questions are answered by DeepSeek (below). Keep `ai` and `@ai-sdk/typesafe-ai` pinned to exact versions.
- **Answer text:** no LLM writes any shown text. In Ask about this stay, DeepSeek (`deepseek-v4-flash`, same setup as search) only picks entry paths from an enum of the knowledge base's entries (max 3, empty = nothing answers); cards show the entry word for word (footnote and markdown symbols removed) with `<Title> · Roam policy` as source. Model or Sanity failure returns 502 and the chat shows a retry, not the support card.
- **Analytics:** PostHog, identified through Clerk. Search sends `stay_search_completed` (`outcome: results | no_results`, counts, `avoided_count`, `interpreter`, filter types, sort, source; never the query text) and `stay_search_failed` (`reason`). ## Rules

- Secret keys (Clerk secret key, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `DATABASE_URL`, `DATABASE_URL_POOLED`, TypeSafe key, Sanity organization token `SANITY_API_CONTEXT_TOKEN`, Sanity write token, `SANITY_API_READ_TOKEN`, `SANITY_API_WRITE_TOKEN`, `HOST_OWNER_SECRET`, `DEEPSEEK_API_KEY`, `SANITY_CONTEXT_KB_URL`) never reach the app bundle. Use them only in API routes and local scripts such as seeding. Never put them behind `EXPO_PUBLIC_`, which is bundled into the app. Never commit `.env`. Keep variable names, without values, in `.env.example`.
- Sanity Context needs a deployed Studio for the dataset. Redeploy Studio from `studio/` after schema changes.
- Jev is not an agent. It answers typed questions (Choice, Noul, Score) with probabilities. It never writes GROQ, calls tools, or generates text. Code builds queries from its answers.
- Prices, guest counts, and dates are parsed in code. Jev may choose between candidates code found, but never produces the value.
- Stay details (`src/app/stay/[id]/index.tsx`, policies form sheet `stay/[id]/policies.tsx`, ask chat `stay/[id]/ask.tsx`, host profile form sheet `stay/[id]/host.tsx`) read one stay from the public CDN through `src/lib/stay-details.ts` (`useStayDetails`, `$id` param, cached for the sheet). House rules and the cancellation policy show Sanity text word for word. "Ask about policies" opens a chat with topic chips and one `AnswerCard` per topic (text plus source label); its replies come from `/api/ask` (`src/lib/ask-policies.ts` holds the chips, copy and fetch). Policies only: stay-specific facts aren't in the knowledge base. The host profile sheet (opened by tapping `HostRow`) reads the host from the cached stay (name, bio word for word, badge) and the host's other stays through `src/lib/host-profile.ts` (`useHostStays`). The bar total is an estimate (nightly price × `minNights` + cleaning fee); "Book this stay" opens modal `stay/[id]/book` (a `presentation: "modal"`, not a form sheet: in a form sheet the pinned Pay footer clipped the top of the content and left the scroll area blank) (calendar from `/api/bookings/availability`, server quote, Pay opens PaymentSheet), then `booking/[id]` polls `/api/bookings/status` and shows the confirmation. Trips lists confirmed bookings (`/api/bookings`, `useBookings` in `src/lib/bookings.ts`); the Profile Trips stat counts them. The heart is persistent (saved stays, below); share uses the native sheet.
- Home reads live stays from the public Sanity CDN through `src/lib/stays.ts` (`useFeaturedStays`, one request for every category; `EXPO_PUBLIC_SANITY_PROJECT_ID` / `EXPO_PUBLIC_SANITY_DATASET` are public values). Search reads Sanity through `src/app/api/search+api.ts` (Clerk-verified with `@clerk/backend`, query built in `src/lib/search-query.ts`, the reading is `readSentence` in `src/lib/search-server.ts`). Code finds the options (`src/lib/search.ts` lists the word tables, known cities, states and amenities; `parseQuery` is the regex fallback and draws chips while loading); the response returns `filters` with `stance: wanted | avoided` ("No pets"), `semantic` and `interpreter: model | fallback | code`, and the screen draws chips from it once ready. Prices, guest counts and places stay code-parsed; the model only says what a number means. Semantic ranking never returns zero, so no-results only comes from hard filters.
- Embeddings rank, they don't filter, and they only see the document itself (no references). Hard constraints are always GROQ filters, and text that should affect ranking lives on the property document.
- Policy answers show only text from the stay's data and Roam's policies, word for word. If nothing answers the question, say so and point to support.
- API routes verify the Clerk session (`getUserId` in `src/lib/api-auth.ts`, never a user id from the body) before doing any work. The one exception is `/api/stripe/webhook`, which verifies the Stripe signature on the raw body instead.
- PostHog failures never block the app. Never send what guests type, tokens, or personal data in events.
- Let Sanity generate document IDs. Model relationships as references.
- Ask before adding a dependency or service, changing the Sanity schema once content exists, or deleting data. Prefer Expo modules over third-party libraries.
- Whenever you need input from the user, ask through your tool's built-in question panel so they pick from options instead of typing. Give two to four clear options with the recommended one first. Fall back to plain text only if no such panel exists.

## How we build features

For a new feature or a change across several files. Small fixes and questions skip this.

1. **Understand.** Read the code involved. Open an earlier plan only if this feature builds directly on it (pick by file name). Read the current docs pages for the APIs you'll use, and load a matching skill if one exists (e.g. the Expo, Clerk, Sanity, Sanity Context, or TypeSafe skills). Don't write version-specific APIs from memory.
2. **Ask.** If a real decision is unclear (scope, visible behavior, data shape), ask in the question panel, batching questions into one round and following up only if the answers raise new ones. Pick defaults for the rest and list them. If a decision in this file looks wrong, raise it instead of changing it.
3. **Plan.** Copy `prompts/TEMPLATE.md` to `prompts/NN-feature-name.md` (next number) and fill it in. The plan must be self-contained, so a fresh session can build it from this file plus the plan alone.
4. **IMPORTANT: stop and wait.** Write no app code until the user approves the plan. Ask for approval in the question panel (approve, or request changes). If they request changes, update the plan and ask again. On approval, set `Status: approved`.
5. **Build** step by step, checking each one. If a step turns out wrong, stop and explain instead of redesigning.
6. **Close out.**
   - Run the plan's Verification and give the report described under Reporting.
   - Add a short `## Result` to the plan and set `Status: done`.
   - Update this file: put each lasting decision in the section it belongs to. Replace or remove rules that are no longer true instead of appending. Keep this file under 150 lines.

## Building from designs

Designs are attached in the chat. Screens must match them exactly: layout, spacing, sizes, colors, type, radii, icons, and copy.

- Icons, fonts, and brand images come from `assets/` or the chosen icon library, never recreated from a screenshot. Sample property photos may be remote placeholder images. If an asset is missing, use a marked placeholder and list it.
- Map every color, font, spacing value, and radius to a design-system token. List values with no token in the plan as proposed new tokens instead of hardcoding them. When creating the design system itself, derive the tokens from the designs.
